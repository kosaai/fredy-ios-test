## Verified Fredy 31.0.0 contracts

Read the installed listingsRouter, API registration, listingsStorage, table filter/sort and detail/media contracts before implementing. A bounded read-only/query_only storage aggregate confirmed that actual coordinates exist; no coordinates, listing IDs, responses, credentials or real fixtures were copied into the repository/index. This aggregate is server-wide evidence of availability, not the number visible to the current signed-in user.

- **GET `/api/listings/map`**, optional exact **`jobId`** query, returns **`{listings: [...]}`**, not a raw array and not a paginated table. It applies existing user/admin/shared-job access rules. Storage selects active (`is_active = 1`), non-manually-deleted rows with both coordinates and neither component equal to the `-1` failure sentinel. The projection includes id/title/price/currency/size/rooms/address/link/provider/latitude/longitude/job_id/job_name/dealType. It omits description, watch and decision metadata.
- **GET `/api/listings/{listingId}`** returns a single authorized, non-hidden stored row plus gallery/affordability fields. Opening a pin reads this exact ID, confirms identity/rental/job scope, then uses the existing ListingRow actions/details and authenticated image loader. Nullable plain description is displayed as text; no provider HTML or remote gallery is loaded automatically. Missing/removed/inaccessible rows show an error, not the stale pin projection as full detail.
- **GET `/api/listings/{listingId}/image`** remains the existing authenticated primary image path. Redirects remain rejected. Upstream can enqueue capture for an uncached image; development tools did not request images or trigger enrichment.
- **GET `/api/listings/table`** remains the real raw-total paginated feed (`totalNumber/page/result`). Its job filter is **`jobNameFilter=<id>`**, different from map `jobId`. Table includes inactive stored rows according to existing filters, while map deliberately requires active rows. Rental-only filtering is client-side; table counts can include other deal types. Offset pagination has no server snapshot/cursor/CAS token.
- **GET `/api/jobs/`** and **GET `/api/dashboard`** remain the real status/count/summary resources. No viewport, map-detail, notifications, geocoding or run-result endpoint is invented.

## Native map

Native iOS 17+ SwiftUI MapKit renders only server-returned rentals with strict numeric finite latitude/longitude in geographic range, excluding either `-1` component. Coordinates are not parsed from addresses, inferred from a provider/city, defaulted or repaired; signed coordinates are independent of nonnegative price decoding. Null/string/malformed/out-of-range coordinates cannot create pins. Repeated IDs yield one marker. Initial camera is automatic, not a fabricated property/location or user-location request.

Selecting a marker opens a native sheet, reads the full stored detail and reuses ListingRow, application letter, original link, watch/status/soft-removal and the single session's images. Selection/detail and map/filter reads have independent generations. Refresh/invalidation clears obsolete pins/selection; late reads cannot resurrect them. Errors/401 route through the existing shared expiry path. Empty means no mappable active rental in scope, not no stored listings or a successful provider search.

The map follows the job selected from Jobs/Listings, without restoring removed chips. Map help explicitly distinguishes its global-per-job active-coordinate scope from text/price/room filters on already-loaded table pages. No automatic geocoding, address editing, detail enrichment, directions, location permission, third-party images, mock markers or new notifications.

## Shared data and refresh rules

The authenticated shell owns AppDataModel: all-jobs rentals shared by Home/unfiltered Listings, one separate selected-job feed, one map snapshot and dashboard state. Home and unfiltered Listings no longer fetch the same first page independently. All rental contexts share the bounded in-memory authenticated thumbnail cache; simultaneous requests for the same image share one Data task and decoding/cache publication is generation-checked.

- The existing transport emits a session-local invalidation after **every attempted authenticated write**, including lost/rejected replies. It is not a successful-write assertion. This covers watch/status/copied application state/recoverable removal, settings saves, Add Search, Edit/Duplicate and Run/Enable/Disable without additional writes or optimistic list copies.
- Card callbacks, real changed Jobs snapshots, confirmed control completion, Add Search result revisions, explicit refresh/retry and foreground return feed the same coordinator. Opening/closing an untouched sheet no longer reloads all data.
- Short 250ms coalescing merges bursts; one owned refresh task drains revision changes. Data invalidation increments generation and clears obsolete pages/pins/summary immediately, including during an older request. Only activated map/selected-job contexts are fetched; there is no request per camera movement. Page/map tasks belong to shared models, not disappearing tabs. Filter changes/expiry explicitly cancel them; a departing consumer cannot cancel another tab's shared read.
- A mutation during an outstanding refresh requests a new pass; stale success, error and cancellation branches cannot publish into newer scope. Refresh resets raw pagination, rental filtering and ID deduplication. Existing client-side filters are kept, and failed initial Home reads can genuinely retry.
- Home, Listings and Jobs pull-to-refresh plus the map's refresh button refresh shared loaded contexts. Dashboard reads now share the same revision barrier instead of publishing independent late Home values.
- Actual accepted Home/Stage 1 manual searches may start **one finite GET-jobs observation window**: at most 12 checks, 5 seconds apart, stopping on an error/expiry, background, observed stop/advanced last-run, or the bound. Changed snapshots trigger coalesced data reads. The window is paused while existing Add Search observation owns its flow, so that flow is not duplicated. No writes/retries/notification calls are in observation. The count is a request bound; slow requests can make elapsed time exceed one minute.
- Existing Add Search's authorized 300-second observation is preserved. No universal live stream or persistent background poll is added. Missing a short run, delayed queue or a run lasting beyond the observation bound remains possible; explicit refresh is available. Stopped/false/last-run/zero never proves provider success.
- 401 from any read/write/image signals shell-wide expiry. Shared rows, pins, selection, dashboard, jobs/editor state, settings drafts/provider metadata, pending search values and image cache are cleared; pending owned work is cancelled. Late editor/search cancellation cannot reverse terminal expiry. Only a fully verified new login resets the transport's expiry signal; the new shell starts clean.

## Boundaries and remaining limits

1. Server coordinates are validated stored facts, **not a claim of survey accuracy**. A geocoded listing may be approximate. Invalid/missing coordinates remain omitted; zero missing-count values are not invented from the map response, which contains no omitted-count field.
2. There is no atomic snapshot across table/map/dashboard/jobs, no cursor pagination and no cross-client idempotency. Generations/deduplication prevent stale local publication and repeated IDs, but cannot guarantee offset completeness while an external writer inserts/reorders rows. Refresh restarts paging.
3. Offline/API failures show real failed states and retry; stale invalidated pins are not silently presented as current. No persistent offline listing store, custom offline tile pack or guaranteed MapKit tile availability is promised. Existing in-memory authenticated images can be reused until expiry.
4. The map endpoint is an unpaginated authorized collection; no unsupported viewport/cursor API, private data fixture or synthetic clustering is introduced. Native render/memory behavior on large accounts requires device testing.
5. Stage 1 notification/channel guards, Stage 2 full-document preservation/uncertainty locks, default template-preview exclusion, Arabic RTL, FindHaus assets and login/top-anchor animation are retained. Hard deletes, Telegram/email/third-party notifications, OAuth/MCP and APNs work remain outside scope. Existing explicit Home bulk-run is preserved, not reconfigured.
